# Mounting Google Drive into pods: `csi-driver-rclone` vs. alternatives

Research notes on whether the `veloxpack/csi-driver-rclone` CSI driver, as currently configured in this repo, is the best-suited way to expose a personal Google Drive folder inside pods — for Shardblade's personal k3s GitOps setup (Argo CD app-of-apps, `CONTEXT.md`). Repo facts treated as given: `templates/apps/csi-driver-rclone.yaml` installs the driver from `oci://registry-1.docker.io/veloxpack/csi-driver-rclone-charts` at `targetRevision: 1.0.0`; `templates/rclone/drive/storageclass.yaml` declares a `StorageClass` with `provisioner: rclone.csi.veloxpakdeck.io` that is **not** currently referenced by any PVC (`storageClassName: ""` on both consumers); `templates/rclone/drive/mounts/storyteller-books.yaml` and `storyteller-beta-books.yaml` are statically-provisioned PV/PVC pairs with `csi.driver: rclone.csi.veloxpack.io`; `templates/rclone/drive/secret.yaml` is an ExternalSecret pulling the rclone remote config from Vault; `storyteller` (`templates/apps/storyteller.yaml`) does not mount `pvc-storyteller` into any container (orphaned resource); `storyteller-beta` (`templates/apps/storyteller-beta.yaml`) was just wired to mount `pvc-storyteller-beta` read-only at `/library` via `accessModes: ReadOnlyMany` + `csi.readOnly: true` + a `readOnly: true` bjw-s `app-template` `globalMounts` entry. Longhorn is already running in this cluster (`templates/apps/longhorn.yaml`, `docs/adr/0008-*` referenced there) — that fact changes the viability of the CronJob-to-PVC alternative discussed below.

Sources are the upstream driver's GitHub repo/README/issues, its docs site, rclone's own docs/forum/GitHub issues, and Kubernetes/CSI docs, cited inline.

## 2. The driver-name mismatch: `rclone.csi.veloxpakdeck.io` vs `rclone.csi.veloxpack.io`

Confirmed: this is a **typo**. The upstream project's actual CSI driver name — used in its own docs, its `RollingUpdate` DaemonSet's `--drivername` default, and matching the org name "veloxpack" — is `rclone.csi.veloxpack.io`, exactly as used in this repo's own static PVs (`storyteller-books.yaml`, `storyteller-beta-books.yaml`). `rclone.csi.veloxpakdeck.io` in `templates/rclone/drive/storageclass.yaml` does not match any real driver and does not appear anywhere in upstream docs, README, or search results — it looks like a copy/paste or autocomplete typo (`veloxpak` + stray `deck`).

**Does it matter today?** No, and that's the more important finding: the `StorageClass` is dead weight. Both consumer PVCs set `storageClassName: ""` and bind by name (`volumeName: pv-storyteller[-beta]`) directly to a statically-provisioned `PersistentVolume`, which is standard practice for static provisioning — [Kubernetes docs, static provisioning](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#static). A `PersistentVolumeClaim` with an empty `storageClassName` and a `volumeName` never invokes the provisioner in `StorageClass.provisioner`; that field, and therefore the typo in it, is only exercised on *dynamic* provisioning (`storageClassName: rclone-drive` on a PVC with no static `PersistentVolume`). So this is a real bug (wrong string, would fail `CreateVolume` if ever used for dynamic provisioning) but currently inert dead code, not a live bug, given this repo only uses static PV/PVC pairs.

## 3. Does the driver actually enforce read-only?

This matters because preventing accidental writes to the user's real Google Drive folder was the explicit point of today's `storyteller-beta` change.

The driver's `NodePublishVolume` handler reads `req.GetReadonly()` (the CSI field Kubernetes populates from the `PersistentVolume.spec.csi.readOnly` field, which itself is driven by the PV's `accessModes` / how the CO mounts it) and, when true, appends the `read-only` flag to the mount options passed into rclone's own mount library before calling `createAndMountFilesystem()` — source inspection of `pkg/rclone/nodeserver.go` in [veloxpack/csi-driver-rclone](https://github.com/veloxpack/csi-driver-rclone). That flag maps onto rclone's own `--read-only`, which rclone's VFS documents as blocking write access at the VFS layer, not merely as a hint — [rclone mount docs](https://rclone.org/commands/rclone_mount/) list it under VFS flags as "Only allow read-only access," and note that on some FUSE implementations (FUSE-T on macOS) write attempts fail *silently* rather than erroring, which is a platform caveat worth knowing but not one that applies to a Linux k3s node.

**Conclusion: this is real enforcement, not cosmetic.** `csi.readOnly: true` in the PV (which this repo sets on `pv-storyteller-beta`) causes Kubernetes to pass `readonly=true` into `NodePublishVolume`, which this driver correctly threads into rclone's VFS as `--read-only`, which rclone's VFS layer enforces by refusing writes at the FUSE level (Linux). The `ReadOnlyMany` access mode on the PV/PVC itself is advisory metadata used for scheduling/validation, not the actual enforcement mechanism — the enforcement is the `csi.readOnly: true` field this repo already set. Today's change does what it was meant to do.

## 4. Known sharp edges of live-mounting Google Drive via rclone/FUSE

| Sharp edge | Detail | Source |
|---|---|---|
| Google API rate limiting on many small files | Google Drive's default quota is ~10 transactions/second per client ID/project, and rclone is commonly described as effectively limited to "about 2 files per second" for file-creation-heavy operations (uploads/renames/deletes) regardless of bandwidth — large files transfer at "100s of MiB/s" but many small files (an ebook library is exactly this shape) hit the per-file-operation ceiling, not the bandwidth ceiling | [rclone Google Drive docs](https://rclone.org/drive/); [rclone forum: aggressive rate limiting](https://forum.rclone.org/t/rclone-mount-of-google-drive-aggresive-rate-limiting-by-google/48420); [rclone forum: best settings for many small files](https://forum.rclone.org/t/best-settings-for-many-small-files-to-google-drive/3014) |
| `403 userRateLimitExceeded` / `rateLimitExceeded` | Common, well-documented error surfaced directly to the mounting application when the quota above is exceeded; forum guidance is to back off (rclone's own advice: wait 24h) or use `--tpslimit`/your own OAuth client ID rather than the shared default | [rclone forum thread](https://forum.rclone.org/t/failed-to-move-googleapi-error-403-user-rate-limit-exceeded-userratelimitexceeded/44068); [rclone Google Drive docs](https://rclone.org/drive/) |
| Shared default OAuth client ID being retired | rclone's docs state the shared default client ID "is being retired and will stop functioning in 2026" and that creating your own client ID is "now required rather than optional" | [rclone Google Drive docs](https://rclone.org/drive/) |
| No real POSIX file locking | rclone's VFS is not a real POSIX filesystem; there is no `flock`/`fcntl` semantics against the remote — an open rclone issue tracks a feature request for remote file locking that does not exist today | [rclone/rclone#7814](https://github.com/rclone/rclone/issues/7814); [rclone mount.md limitations](https://github.com/rclone/rclone/blob/master/cmd/mountlib/mount.md) |
| Write behavior depends entirely on `--vfs-cache-mode`, which this repo does not set | rclone's own default is `off`; in `off` mode, "files opened for write can't be seeked" and existing files opened for write "must have O_TRUNC set" — i.e. no local buffering, writes go straight to the API one file at a time, maximizing exposure to the rate limits above | [rclone mount docs](https://rclone.org/commands/rclone_mount/) |
| Node-plugin crash/OOM → stuck mount | An open-source user of this exact driver reported the rclone node-plugin container being OOM-killed (memory spiking >300 MB) and the consuming pod's mount then failing with `Transport endpoint is not connected`; restarting the DaemonSet alone did not recover it — the **consumer pod** also needed a restart | [veloxpack/csi-driver-rclone#58](https://github.com/veloxpack/csi-driver-rclone/issues/58) |
| OAuth-token refresh bugs in this specific driver (fixed, but recent) | Closed issue #54 reported the driver (unlike a raw `rclone` process) not refreshing an OAuth token, breaking the mount after 60–90 minutes; scoped to OneDrive/SharePoint auth, fixed via PR #57 — evidence the driver's OAuth-refresh plumbing is young code that has had at least one real bug in exactly the class of failure a Drive remote also depends on (refresh-token renewal) | [veloxpack/csi-driver-rclone#54](https://github.com/veloxpack/csi-driver-rclone/issues/54) |
| `reclaimPolicy: Delete` doesn't delete remote content | Open issue #64 reports that `Delete` reclaim policy on this driver's PVs doesn't actually delete the underlying remote files — irrelevant here since this repo already sets `persistentVolumeReclaimPolicy: Delete` on the static PVs pointed at real Drive folders, but worth knowing the field doesn't mean what it says | [veloxpack/csi-driver-rclone#64](https://github.com/veloxpack/csi-driver-rclone/issues/64) |
| Reschedule / node change | Not a documented problem specific to this driver: CSI node plugins are DaemonSets, and `NodePublishVolume` is re-invoked by kubelet on whichever node the pod lands on, which is the standard CSI contract — [CSI spec / Kubernetes CSI docs](https://kubernetes-csi.github.io/docs/) — no primary source found describing this driver failing that contract specifically, only the OOM/stuck-mount failure mode above (which is a driver-health problem, not a scheduling one) |

## 5. Alternatives comparison

### a. CSI driver (current approach)

Dynamic (`StorageClass`, unused here) vs. static (`PV`/`PVC` pair, what's actually deployed) provisioning: static provisioning is a reasonable choice for "one Drive folder, one purpose-built PV" and avoids ever exercising the buggy `provisioner:` string. Blast radius per PVC is contained to whichever pod mounts it, and read-only enforcement is real (§3). Downsides are entirely upstream-driver maturity: a one-year-old, single-org, Apache-2.0 project with 9 open issues including at least one stuck-mount failure mode requiring manual pod restart (§4) and a data-loss-adjacent reclaim-policy bug that doesn't apply here but signals surface area.

### b. `rclone mount`/`cmount` as sidecar/init container (classic homelab pattern)

The commonly-blogged pattern: a container in the same pod runs `rclone mount`, requires `securityContext.capabilities.add: [SYS_ADMIN]` and `/dev/fuse` device access, and shares the resulting mount into the app container via an `emptyDir` with propagation set to `Bidirectional`/`HostToContainer` — [example writeup](https://blog.init-io.net/post/2024/kubernetes-rclone-mount/); mount-propagation mechanics documented at [kubernetes/kubernetes#46643](https://github.com/kubernetes/kubernetes/issues/46643). A separate `rclone` maintainer-tracked issue shows the common failure mode when this is done wrong: mounting into a `hostPath` puts the FUSE mount only inside the container's own mount namespace, so the host (and other containers via hostPath) sees an **empty directory** — [rclone/rclone#5637](https://github.com/rclone/rclone/issues/5637). Done correctly (emptyDir + propagation, not hostPath) it works, but every pod that wants the mount carries its own `SYS_ADMIN`-capable sidecar — broader per-pod privilege than a CSI driver, whose elevated capability lives once in a DaemonSet instead of in every consuming pod. For a single-tenant homelab this is a real but modest security regression versus the CSI approach, not a blocker; it does, however, reproduce every rclone/Drive sharp edge in §4 with less mature glue code than a purpose-built CSI driver, and none of the "restart pod on stuck mount" problem goes away — it just moves into a sidecar you own instead of a DaemonSet someone else maintains.

### c. Scheduled `rclone sync`/`copy` (CronJob) into a normal RWO PVC — e.g. Longhorn

**Longhorn is already running in this cluster** (`templates/apps/longhorn.yaml`), which makes this the cheapest alternative to stand up: a `StorageClass: longhorn` (or `longhorn-low`, both already present) PVC, and a `CronJob` that runs `rclone copy`/`sync` (one-directional mirror; not `bisync`, which rclone's own docs warn is an advanced, riskier bidirectional command "read and understand the entire manual… before using, as data loss can result" — [rclone bisync docs](https://rclone.org/bisync/)) from the Drive remote into that PVC on a schedule. This trades live-ness (new Drive files appear only after the next CronJob run, not instantly) for reliability: no long-lived FUSE process to OOM or get "Transport endpoint not connected," no per-request rate-limit exposure to the serving pod (only the periodic sync job talks to the Drive API, batched, and can retry/backoff independently of the app), and the consuming pod gets a completely ordinary Longhorn-backed volume with normal POSIX semantics (real locking, real random writes, no VFS cache-mode tuning needed). This is a materially better fit for the **read-only, auto-import** `storyteller-beta` `/library` use case specifically, where near-real-time freshness was never a stated requirement — the entire point was "keep the source folder safe from writes," and a one-way `copy` job structurally cannot write back to Drive at all (no `--read-only` flag reliance, no driver-enforcement question, because the mechanism has no write path into Drive to begin with).

### d. Other maintained rclone-CSI projects

Already covered in §1's table — [wunderio/csi-rclone](https://github.com/wunderio/csi-rclone) is the only other project in this space with comparable recent activity (pushed 2026-08-18); everything else (dvcrn's and almahmoud's forks) is a small, low-activity fork of wunderio predating veloxpack's driver. There is no `kubernetes-csi`-org (i.e. SIG-Storage-sanctioned) rclone driver — this entire category is community-maintained, single-or-small-org software, which is a structural risk shared by every CSI option, not specific to veloxpack.

### Comparison table

| Option | Live-ness | Write safety for read-only use case | Privilege footprint | Failure mode | Maturity | Fit for `storyteller-beta` `/library` (RO) | Fit for `storyteller` `/data` (RW, if ever wired) |
|---|---|---|---|---|---|---|---|
| **CSI driver (current)** | Live | Real enforcement via `csi.readOnly` → rclone `--read-only` (§3) | One DaemonSet holds the FUSE capability | Node-plugin OOM → stuck mount, needs pod restart (#58) | 1 yr old, 9 open issues, active | Good, works today | Workable but exposed to every rate-limit/caching edge in §4 with no local buffering (`vfs-cache-mode` unset → `off`) |
| **Sidecar `rclone mount`** | Live | Same rclone `--read-only` flag available, same real enforcement | `SYS_ADMIN` + `/dev/fuse` per consuming pod | Same FUSE fragility, now duplicated per pod; hostPath misconfig silently empties (#5637) | Rclone itself is mature; the pattern is DIY glue | Workable, no better than CSI, more privilege | Same sharp edges as CSI, more privilege, no upside |
| **CronJob `rclone copy`/`sync` → Longhorn PVC** | Periodic (cron interval) | Structural: sync direction is one-way, no write path back to Drive exists | None beyond the CronJob's own pod | Job fails/retries independently of the serving pod; serving pod never sees Drive/API errors | rclone `sync`/`copy` are core, long-stable commands; Longhorn already in this cluster | **Best fit** — matches the "auto-import, no live edits needed" use case exactly | Wrong shape if genuine live read-write to Drive is required; right shape if "periodically push local writes back" is acceptable |

## 6. Verdict

### Recommended

1. **For `storyteller-beta` `/library` (the new read-only auto-import mount): keep the CSI driver for now, but treat a CronJob-based one-way `rclone copy`/`sync` into a Longhorn PVC as the preferred next iteration.** The current wiring (`csi.readOnly: true`, `accessModes: ReadOnlyMany`) is correctly configured and the driver does genuinely enforce read-only at the FUSE layer (§3) — there is no data-loss risk in the setup as it stands today. But the read-only use case's own requirements (an app auto-importing a static book collection, not editing it) don't need live-ness, and a scheduled sync sidesteps essentially every sharp edge in §4 at once: no long-lived FUSE process to OOM, no per-request Drive-API rate-limit exposure on every `ls`/open from the app, no dependence on this driver's one-year-old OAuth-refresh code path. Longhorn is already running in this cluster, so the infrastructure cost of this switch is one `CronJob` manifest plus a normal PVC, not a new subsystem.
2. **Patch the driver-name typo regardless of which path is chosen**: `templates/rclone/drive/storageclass.yaml`'s `provisioner: rclone.csi.veloxpakdeck.io` should read `rclone.csi.veloxpack.io` to match the driver actually installed and the string already used correctly in both static PVs. This costs nothing and removes a landmine for whoever next tries to use the `StorageClass` for dynamic provisioning and gets a confusing `CreateVolume` failure.
3. **If staying on the CSI driver for either use case, set `mountOptions: [vfs-cache-mode=writes]` (or `full`) explicitly** rather than relying on the unset default (`off`). `off` mode forces every write straight through to the Google Drive API with no local buffering, which is the single easiest way to trip the small-files rate limit described in §4 — this only matters if `storyteller`'s `/data`-style read-write mount is ever actually wired up (see below), since the current read-only mount never writes at all.

### Not recommended

- **Wiring up `storyteller`'s orphaned `pvc-storyteller` as a genuine read-write Drive mount without first adding `vfs-cache-mode` and understanding the rate-limit/locking caveats in §4.** A book-management app doing live read-write against a FUSE-mounted Drive folder with no cache buffering is the worst-case shape for Google's per-file-operation rate limits (many small file writes/renames), and rclone's own docs are explicit that this needs deliberate tuning, not defaults.
- **Switching to the sidecar `rclone mount` pattern.** It carries strictly more privilege (`SYS_ADMIN` + `/dev/fuse` in every consuming pod instead of once in a DaemonSet) for no reduction in any of the sharp edges in §4 — it is the same rclone FUSE code underneath, just with the elevated capability moved to a place with a larger blast radius. Not worth it unless a specific need arises to avoid depending on the veloxpack driver's DaemonSet entirely.
- **Migrating to `wunderio/csi-rclone` or its forks.** Marginally more mature by age, but lower current activity/stars and more open issues than veloxpack's driver, and no evidence it has solved any of the sharp edges in §4 (rate limiting, locking, cache-mode tradeoffs are properties of rclone itself, inherited by every CSI wrapper equally). No compelling reason to switch drivers within the same architecture.
